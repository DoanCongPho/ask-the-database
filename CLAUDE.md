## AI usage log (required, every prompt)

The submission is judged partly on how AI tools were used. After handling **each** user prompt, append a numbered entry to `AI_USAGE_LOG.md` using the format already in that file:
- **Asked:** the user's prompt (verbatim if short, otherwise a faithful summary).
- **AI did:** what was produced or changed (files, key decisions).
- **Checked:** what was actually verified (ran the app, ran a query, tested a question), and what was *not* verified. Be honest; don't claim checks that weren't run.
- **Fixed / rejected:** AI output the user corrected, rejected, or asked to redo, plus mistakes the AI found in its own earlier output and fixed. Record the original approach and why it changed.

Keep entries short. When the user pushes back on something, log it in the next entry even if they only said it in passing.

## Frontend commands (run in `frontend/`, bun lockfile)

```bash
bun install
bun run dev            # http://localhost:5173 ; env from frontend/.env (see .env.example)
bun run test           # vitest; single file: bunx vitest run src/test/format.test.ts
bun run lint           # eslint + prettier; fix formatting with: bunx prettier --write src/...
bunx tsc --noEmit -p . # typecheck
```

`VITE_USE_MOCK=true` routes every call in `src/lib/api.ts` to `src/lib/mock.ts`, so the UI works without the backend. The mocks use the real schema and are the reference for response shapes. The contract is `src/lib/types.ts` (`AskResponse`), and the backend must match it.

## Backend commands (run in `backend/`)

```bash
uv venv .venv && uv pip install -p .venv -r requirements.txt   # or python -m venv + pip
cp .env.example .env                       # set LLM_API_KEY / LLM_BASE_URL / LLM_MODEL / DATABASE_URL
.venv/bin/uvicorn app.main:app --reload --port 8000
.venv/bin/python -m pytest -q tests        # DB tests skip if Postgres is down; LLM is faked
.venv/bin/python -m pytest -q tests/test_safety.py -k delete   # single test
.venv/bin/python -m scripts.eval --show-sql   # live LLM run over scripts/eval_questions.json
```

Locally, Postgres runs on **port 5433**, because 5432 is used by another project's container (`mrson_rag_db`, not ours, don't touch it). After `seed.sql`, also run `docker exec -i shop-db psql -U postgres -d shop < db/readonly_role.sql`.

Read-only is enforced in layers. Don't remove one because another exists:
1. The prompt tells the LLM to refuse writes.
2. `safety.check_sql` (sqlglot) requires a single SELECT, rejects any write node or `pg_*` function, and allows only the 4 tables.
3. The `shop_reader` role has SELECT-only grants.
4. Each query runs in `SET TRANSACTION READ ONLY` with a statement timeout, and the transaction is always rolled back.

The role's `default_transaction_read_only` can be switched off by the session itself, which is why 3 and 4 both exist. `tests/test_db.py` proves the DB layer holds even with the validator skipped.

## UX decisions (from the user, keep them)

- The target user can't read SQL. There's no SQL editing: SQL is shown collapsed for transparency only. Answers are refined in plain language through follow-ups that send the card's question and SQL as `history`.
- The AI's reasoning is shown as plain-Vietnamese `steps` behind "Xem cách tôi tìm câu trả lời".
- **Ask, don't guess:** ambiguous metrics ("tốt nhất", "được yêu thích nhất") get `clarify` with 2–4 options. Things with a sensible default (no date range means all data, no N means top 5) are not clarified; the default is stated in `interpretation`.
- All UI and AI text is Vietnamese, even for English questions. Money is `1,234,000 ₫`, dates `dd/MM/yyyy`, months `Tháng 10/2025`. The backend must send dates as `YYYY-MM-DD` (cast `date_trunc` results to `::date`).
- The summary never counts or sums the 20 sample rows. `pipeline._stats` computes counts per category, min/max and sums over **all** rows (no sums of prices or averages). For a truncated result it sends no stats and says "ít nhất N".
- No RAG. The schema fits in the prompt; use static, DB-verified few-shot examples that aren't the test questions.
- **General questions** ("bạn làm được gì?", "có những bảng nào?", greetings) get `kind: "info"` and `status: "info"`: a plain-words message, example-question chips, and the table list from `app/schema_info.py`, which is never written by the LLM.
- **Split, don't combine:** a question with 2–3 independent asks (e.g. "top customer *and* top product") gets `kind: "split"`. Each part runs through the full pipeline on its own, in parallel, and the response is `status: "multi"` with `parts[]`. One part failing doesn't break the others, and each part gets its own table, chart and refine box.
- **Conversations:** "Cuộc trò chuyện mới" starts an empty conversation, and only the open conversation is sent as context. `history` carries what the owner saw (status, summary or message, clarify options, column names, the first 5 rows), not just the SQL, so follow-ups like "người đứng đầu…" resolve against the previous result. No Kafka or result cache: the data is static and small, and the LLM call is the latency.

## Goal

Build a web app (not a CLI) for a non-technical shop owner: they type a question in plain language, an LLM generates SQL, the app runs it against PostgreSQL, and the page shows the SQL and the result. Any language, framework, or LLM provider is allowed.

## Run everything with Docker

```bash
docker compose up --build -d      # db + backend + frontend → http://localhost:3000 (API on :8000)
docker compose down -v            # stop and wipe the DB volume (next up re-seeds it)
FRONTEND_PORT=3001 BACKEND_PORT=8001 docker compose up --build -d   # if ports are busy
docker compose exec backend python -m pytest -q tests
docker compose exec backend python -m scripts.eval --show-sql
```

- The backend reads `backend/.env` (LLM settings). Compose overrides `DATABASE_URL` and `CORS_ORIGINS`.
- The DB has no host port. It seeds from `seed.sql` + `db/readonly_role.sql` only on an empty volume.
- `VITE_*` values are baked in at build time. The frontend image builds with `NITRO_PRESET=node-server`, because the Lovable default is Cloudflare.
- The pipeline is explained with diagrams in `docs/PIPELINE.md`.

## Database

```bash
docker run -d --name shop-db -p 5432:5432 \
  -e POSTGRES_USER=postgres -e POSTGRES_PASSWORD=postgres -e POSTGRES_DB=shop \
  postgres:16
docker exec -i shop-db psql -U postgres -d shop < seed.sql      # load / reset data
docker exec shop-db psql -U postgres -d shop -c "SELECT COUNT(*) FROM orders;"   # → 700
docker rm -f shop-db                                             # tear down
```

Connection: `postgresql://postgres:postgres@localhost:5432/shop` (use `-p 5433:5432` and port 5433 if 5432 is busy).

Schema (4 tables): `customers(id, name, city, created_at)`, `products(id, name, category, price_vnd)`, `orders(id, customer_id, order_date, status)`, `order_items(id, order_id, product_id, quantity, unit_price_vnd)`.

Facts the LLM prompt and the UI need to get right:
- Revenue/spending counts **only** `orders.status = 'paid'` (statuses: `paid`, `pending`, `cancelled`).
- Revenue = `SUM(order_items.quantity * order_items.unit_price_vnd)`. `unit_price_vnd` is the price at order time (may be discounted). `products.price_vnd` is the *current* list price, so don't use it for revenue.
- Money is VND (integers), displayed like `1,234,000 ₫`.
- Data covers `2025-01-01` to `2026-10-12`: 100 customers, 20 products, 700 orders.
- Enumerated values: cities `'Ha Noi', 'TP.HCM', 'Da Nang', 'Can Tho'`, categories `'drink', 'snack', 'household', 'personal care'`.

## Hard requirements (from the brief)

1. Question → SQL → execute → show both the SQL and the result.
2. The app must **never** modify data. Enforce this at the DB level (read-only transaction or role), not only with keyword filtering of the LLM output.
3. The app never crashes. Every failure shows the user a clear message on the page.
4. A real UI with clickable example questions; SQL visible but not in the way; a readable table with formatted numbers/dates that stays usable at hundreds of rows; distinct states for loading, no results, error, refused, and "please clarify"; session question history.
5. Bonus: if SQL fails, retry with the DB error fed back to the LLM.

Other rules:
- Read the LLM API key, base URL, and model name from env vars or `.env`. Never commit the key (keep `.env` gitignored and provide `.env.example`).
- Do not change the data. Do not hand-write SQL for the test questions: answers must come from the LLM.

## Test questions and their intended edge cases

1. How many customers are there?
2. Top 3 customers by total spending (paid only)
3. Customers who never placed an order
4. Monthly revenue in 2025 (good fit for a chart)
5. List all orders from 2024. **User decision (2026-10-20):** "from/từ 2024" means 2024 onwards, so the answer is all 700 orders (2025–2026), and the summary says none are from 2024. "in/trong năm 2024" means only that year, which gives the **empty** state with the available date range (eval: "Đơn hàng trong năm 2024").
6. Show employee salaries: **no such table**. The app should say the data isn't available instead of making up SQL.
7. Delete all cancelled orders: write request, must be **refused**.
8. What is the best product?: **ambiguous** (by revenue? quantity?). The app returns `clarify` with options (theo doanh thu / số lượng bán / số đơn hàng). It does not guess.

Evaluators will also try new questions not on this list.
